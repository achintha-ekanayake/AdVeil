# AdVeil — Design Document

Cross-browser overlay + ad blocker extension (Manifest V3).

## Context
The project directory (`Add-blocker`) is currently empty - this is a greenfield build, not git-initialized yet. The user wants a browser extension for both Firefox and Chrome that blocks **overlaying ads** (full-screen interstitials, sticky popups, anti-adblock nags, cookie-wall-style ad overlays that cover page content). Based on clarifying answers, the scope was expanded to also include **general ad blocking** (network-level domain blocking + generic cosmetic hiding), using a **hybrid detection approach** (heuristic DOM analysis as the primary/original mechanism + a curated filter-list layer for precision), built as a **single Manifest V3 codebase** loadable unpacked in both Chrome and Firefox, with a **toolbar popup UI** (on/off toggle, per-site pause, blocked-count display).

The overlay-heuristic engine is the core original value; the network/cosmetic ad blocking is an intentionally-scoped-down "mini ad blocker" layer (curated few-hundred-domain list, not a full EasyList import) so the MVP stays buildable.

## File Structure
```

├── README.md                       # load-unpacked instructions, scope notes
├── icons/{16,32,48,128}.png

├── popup/{popup.html,popup.js,popup.css}
├── rules/

│   ├── overlay-selectors.json      # curated CSS selectors for known overlay patterns
│   ├── generic-ad-selectors.json   # curated CSS selectors for generic ad containers
│   ├── build-dnr-rules.js          # Node script: domains-source.txt -> generated/dnr-rules.json
│   └── generated/dnr-rules.json    # build output, checked in, referenced by manifest.json
└── test/overlay-test.html          # dev-only fixture page (not shipped/referenced in manifest)
```

## manifest.json
- `manifest_version: 3`, permissions: `declarativeNetRequest`, `storage`, `activeTab`, `scripting`, `tabs`; `host_permissions: ["<all_urls>"]` (required since protection must run proactively on every page, not just on click - document this trade-off in README).
- `background`: dual-key object - `service_worker` (Chrome) + `scripts` (Firefox) both pointing at `background/service-worker.js`. **Do not use ES module `import`/`export`** in that file - flat script avoids module-vs-classic-script cross-browser ambiguity; drop `"type": "module"`.
- `action.default_popup: popup/popup.html`.
- `declarative_net_request.rule_resources`: one static ruleset pointing at `rules/generated/dnr-rules.json`.
- `content_scripts`: `cosmetic-filter.js` + `overlay-engine.js` on `<all_urls>`, `run_at: document_start`, `all_frames: false` (top frame only). This is a real coverage cut, not just a cross-origin limitation: some overlay ads (and their close-button-hijacking scripts) render inside **first-party** iframes too, which this misses. Fine as an MVP trade-off, but the README must say this plainly rather than implying only cross-origin ad iframes are excluded.
- `browser_specific_settings.gecko.id` set for Firefox loading - pick a stable value now; changing it later changes the extension's identity for storage/update purposes, so don't treat it as a placeholder to revisit casually.
- No `web_accessible_resources` needed for MVP. Default CSP is expected to be sufficient for extension pages (popup/background use no remote scripts or eval) - worth a one-line confirmation once manifest.json is actually written, not assumed silently.

## Network blocking (declarativeNetRequest)
- `rules/domains-source.txt`: curated plain-text list (a few hundred well-known ad/tracker domains, `#`-commented, hand-picked from public knowledge of common ad networks/trackers - e.g. doubleclick.net, googlesyndication.com, adnxs.com, scorecardresearch.com). Explicitly **not** a full EasyList import.
- `rules/build-dnr-rules.js` (plain Node, no deps): reads the source list, dedupes, emits one DNR block rule per domain using `||domain^` urlFilter syntax, `resourceTypes` excluding `main_frame` (never block a page the user directly navigates to), asserts rule count stays well under DNR limits, writes pretty-printed JSON to `rules/generated/dnr-rules.json`. Checked into repo so unpacked-load works with zero build step; script only reruns when the domain list changes.
- **Firefox DNR parity is not guaranteed** even for this static-rules-only subset - Firefox's `declarativeNetRequest` implementation has historically lagged Chrome's, and a mismatch here can fail silently (rules just don't apply, no error thrown). Confirm early, as part of first-load verification, that Firefox actually honors `rule_resources` the same way Chrome does - don't assume parity because only the "safe" static-rule subset is used.

## Cosmetic filtering (`cosmetic-filter.js`)
- Curated selector lists (`overlay-selectors.json` ~30-60 entries for overlay-specific patterns, `generic-ad-selectors.json` ~50-100 entries for common ad containers like `.adsbygoogle`) inlined as JS constants in the script for synchronous availability at `document_start` (no fetch race).
- Injects one `<style>` tag with `selector1, selector2, ... { display: none !important; }`.
- Skips entirely if globally disabled or current site is whitelisted (checked via `chrome.storage.local` before injecting).

## Overlay heuristic engine (`overlay-engine.js`) - core feature
- **Signals** (weighted, summed into a score): `position: fixed/sticky`, high `z-index`, viewport-coverage ratio (`getBoundingClientRect()` vs window size), body scroll-lock (`overflow:hidden`) correlated with the element's insertion, delayed appearance after `DOMContentLoaded` (>~1.5s), ad-keyword substrings in id/class, presence of an ad-network iframe. A numeric `HIDE_THRESHOLD` constant (named, easy to later expose as a "sensitivity" setting) triggers hiding once cleared.
- **Attach timing**: the script runs at `document_start`, where `document.body` does not exist yet - do not assume it does. Use a one-shot `readystatechange`/`DOMContentLoaded` listener (or a short poll via `requestAnimationFrame` if body appears before that fires) to attach the `MutationObserver` to `document.body` only once it exists. This must be built and tested explicitly, not assumed to "just work."
- **MutationObserver**, debounced ~150-250ms batching, pre-filtered to reasonably-sized block elements (`offsetWidth/Height > 50`) before scoring. Supplemented by a periodic shallow rescan (catches display-toggle-only overlays that don't add new nodes) on a **decaying schedule** (e.g. check at 1s, 3s, 6s, 10s, then stop) rather than a fixed cadence for a full 60s - keeps the perf/battery cost bounded across many open tabs. Paused entirely when the tab is hidden (`visibilitychange`).
- **Hide, not remove**: hide via `element.style.setProperty('display', 'none', 'important')` directly on the element (inline style + `!important` reliably beats page stylesheet specificity) rather than an injected class, which a highly-specific page rule could outrank. Reversible and won't break page JS holding references. Records hidden elements (WeakMap or tagged data-attribute) for a same-page "restore hidden elements" popup action.
- **Whitelist/enabled short-circuit**: checked first, before attaching any observer - global `enabled` flag and per-site `siteWhitelist` (hostname list) in `chrome.storage.local`.
- **False-positive risk is structural, not incidental**: legitimate full-screen UI (cookie-consent banners, onboarding modals, paywalls, expanded chat widgets) scores similarly to ad overlays on several signals at once (fixed position, high z-index, viewport coverage, scroll-lock). Budget real tuning time for this beyond a single pass. In `DEBUG` mode, log the **per-signal score breakdown** (not just the summed total) for every evaluated candidate, so tuning against real sites is diagnostic rather than trial-and-error against one number.

## Messaging & badge
- Content scripts → background: `OAB_ELEMENT_BLOCKED` (increment), `OAB_COSMETIC_COUNT_SYNC` (absolute count reconcile), via `chrome.runtime.sendMessage`.
- Popup ↔ background: `OAB_GET_TAB_STATS` / response; toggle state changes (`enabled`, per-site whitelist) go **directly through `chrome.storage.local` writes from the popup**, with content scripts and background reacting via `chrome.storage.onChanged` - simpler than round-tripping toggles through explicit messages. Reserve `runtime.sendMessage` for count-reporting and the `OAB_RESTORE_HIDDEN` popup→content-script action.
- Background keeps an in-memory (mirrored to `chrome.storage.session` where available, falling back to plain in-memory `Map` if unsupported) per-tab counter map, updates `chrome.action.setBadgeText` on change, resets counters on `chrome.tabs.onUpdated` (status `loading`, main frame) and cleans up on `chrome.tabs.onRemoved`.
- **Service-worker restart handling**: Chrome can terminate and restart the service worker at any point. On worker startup, explicitly rehydrate the per-tab counter map from `chrome.storage.session` *before* handling any new message or setting a badge - otherwise there's a window where a restart mid-tab-session shows a stale/zero badge until the next event arrives. Treat this as a required startup step, not an edge case.
- **Firefox background lifecycle differs from Chrome's service worker** (event-page `persistent: false` semantics, different wake timing on `onMessage`/`onInstalled`). Verify early - before writing the bulk of the other files - that a content script's `OAB_ELEMENT_BLOCKED` message reliably wakes the background script in Firefox and is not silently dropped. This is a "test first" risk item, not a footnote.
- **Known MV3 limitation**: production builds can't get exact per-request network-block counts (the debug API is dev-mode/unpacked only) - badge/popup counts reflect overlay + cosmetic hides only; network blocking still runs, just isn't counted. Document this clearly rather than treating it as a bug.

## Storage schema (`chrome.storage.local`)
```js
{
  enabled: true,
  siteWhitelist: ["example.com", ...],   // exact hostnames, MVP simplification
  stats: { totalOverlaysBlocked: 0, totalCosmeticBlocked: 0, installDate: "..." },
  schemaVersion: 1
}
```
Per-tab ephemeral counts in `chrome.storage.session` (or in-memory fallback), keyed by tabId.

`schemaVersion` must be backed by an actual migration check on background startup (e.g. `chrome.runtime.onInstalled`/on-load comparison against the current schema constant, applying migrations as needed) - otherwise it's a decorative field, not a real safeguard. Build this check even though there's only one schema version at MVP time, so future bumps aren't the first time it's exercised.

## Popup UI
Vanilla HTML/JS/CSS (no framework/bundler - scope creep for this size): header with global on/off toggle; current-tab hostname with a "paused on this site" toggle; "Ads blocked on this page" count (overlay + cosmetic only, per the counting limitation above); a secondary "Restore hidden elements on this page" button sending `OAB_RESTORE_HIDDEN`. No options page - matches the user's explicit scope choice; whitelist pruning UI is the one clear future candidate if ever needed.

## Verification
1. **Load unpacked**: Chrome via `chrome://extensions` → Developer mode → Load unpacked (project root). Firefox via `about:debugging#/runtime/this-firefox` → Load Temporary Add-on (select `manifest.json`).
2. **Early cross-browser sanity checks (do these before writing the bulk of remaining code, not just at the end)**: (a) confirm a content-script message (`OAB_ELEMENT_BLOCKED`) reliably wakes and is handled by the Firefox background script, not silently dropped by event-page lifecycle differences; (b) confirm Firefox actually applies the static `rule_resources` DNR ruleset the same as Chrome (check DevTools Network tab for a blocked request on both browsers) - this can fail silently on Firefox, so verify directly rather than assuming parity.
3. **Fixture test page** (`test/overlay-test.html`, dev-only, not referenced by manifest): includes (a) a delayed (2s) full-screen fake "disable your ad blocker" overlay with scroll-lock, to verify high-score detection; (b) a sticky-footer nag fixture for mid-range scoring/tuning; (c) **multiple** negative-control fixtures, not just one - a cookie-consent banner, an onboarding modal, and a paywall-style overlay, each legitimate (no delay, no scroll-lock, no ad keywords) but sharing surface signals (fixed position, high z-index, viewport coverage) with real ad overlays - all must remain visible. A single negative fixture is not enough to surface this class of false positive. Serve via `python3 -m http.server` or open as `file://` (enable "Allow access to file URLs" in `chrome://extensions` for the latter). Use the `DEBUG` per-signal score breakdown to tune `HIDE_THRESHOLD`.
4. **Network blocking check**: DevTools Network tab on a real ad-heavy page, confirm requests to curated domains are blocked; confirm the domain build script (`node rules/build-dnr-rules.js`) regenerates `dnr-rules.json` correctly after editing `domains-source.txt`.
5. **Manual spot-check**: 2-3 real ad-laden sites to visually confirm overlay/cosmetic removal and toggle/whitelist/restore behavior in the popup, including reloading mid-session to confirm badge counts rehydrate correctly after a simulated service-worker restart (Chrome DevTools → Application → Service Workers → "Terminate" while a tab has active counts, then trigger another block and confirm the badge updates from the rehydrated count rather than resetting to zero unexpectedly).

## Explicit MVP scope limits
No full EasyList import (curated domain list only); no regex/path filter rules, no `main_frame` network blocking; no cross-origin iframe scanning (`all_frames: false` applies to **both** `overlay-engine.js` and `cosmetic-filter.js` - generic ad-container hiding is missed inside first-party iframes just as much as overlay detection is; phrase the README caveat as covering both mechanisms, not just the heuristic engine); no options page; no exact production network-block counter (platform limitation); no persistent cross-session undo (session-only restore, whitelist toggle is the durable fix); no automated test harness (manual fixture + spot-checks only); detection threshold is a hard-coded constant needing empirical tuning before relying on it broadly; **no SPA/pushState navigation handling** - content scripts run once per real document load, so on single-page apps the periodic rescan window can lapse, `chrome.tabs.onUpdated`'s `status: 'loading'` won't fire on a pushState-only route change to reset per-tab counters, and overlays injected later in an SPA's lifecycle may go undetected. To be precise about the failure mode: a user who lands on an SPA, waits past the rescan window (the MutationObserver keeps running, but its debounced-batch pre-filtering and the specific timing signals tuned around "just loaded" no longer line up the same way), then navigates client-side into a route that shows a delayed overlay gets **zero** heuristic coverage for that overlay, not degraded coverage - this is an absence, not a weaker version of the normal case. Acceptable MVP gap, called out explicitly rather than discovered during spot-checks; a `history.pushState`/`popstate` hook to re-arm the rescan window is the natural post-MVP fix; **counter continuity across service-worker restarts is best-effort, not guaranteed, when `chrome.storage.session` is unavailable and the in-memory `Map` fallback is used** - a worker restart in that combination legitimately resets the badge to zero, and the verification step confirming rehydration should be read as covering the `storage.session`-available case, not promising continuity in the fallback case.

## Small implementation-time checks (not architecture changes)
- `activeTab` is likely redundant once `host_permissions: ["<all_urls>"]` is granted (the latter supersedes it). Harmless to keep, but if minimizing the requested permission set matters for store review later, drop it or note explicitly why both are kept.
- When generating DNR rules, confirm `resourceTypes` explicitly includes `sub_frame` (a lot of ad delivery is via ad iframes) - the plan excludes `main_frame` deliberately, but don't let that exclusion accidentally take `sub_frame` down with it.
- Guard against double-counting: an element can simultaneously match a cosmetic CSS selector and clear the heuristic score threshold (common for ad containers with ad-keyword classes), which could fire both `OAB_ELEMENT_BLOCKED` and inflate `OAB_COSMETIC_COUNT_SYNC` for the same element. Tag elements already hidden by the cosmetic CSS pass with an explicit marker (a data-attribute set by `cosmetic-filter.js`) and treat **that marker, not `getComputedStyle(el).display === 'none'`, as the sole source of truth** for the heuristic engine's skip check - computed style is also true for elements the page itself legitimately hides, which would cause the heuristic engine to skip content it should never have been evaluating in the first place and mask the real dedupe signal. Make this explicit in the code so it isn't implemented the ambiguous way under time pressure.

## Live-testing findings (2026-08-14, post-build verification)

Built end-to-end, then verified with a scripted Chromium (Playwright) session - the unpacked extension loaded, navigated to a real ad-heavy streaming site (a movie-player page with a persistent fixed banner ad overlapping the video), plus the fixture page. Two real defects surfaced that pure code review and the fixture page alone did not catch:

1. **Fatal cross-script namespace collision (found first, was masking everything else).** `overlay-engine.js` and `cosmetic-filter.js` share one global scope per frame (see manifest.json content_scripts order - this was known, but its implication wasn't fully worked through). Both files independently declared `let oabRescanTimers`, `function oabScheduleRescans`, `function oabInit`, and `function oabIsWhitelisted`. The duplicate `let` is a **fatal SyntaxError** that silently killed all of `overlay-engine.js` on every page - the heuristic engine never ran at all, with no visible error outside the page's own DevTools console (confirmed via `page.on('pageerror')` in the test harness; a manual glance at the popup/badge would just have shown "0 blocked" with no indication why). Fixed by prefixing every `cosmetic-filter.js` top-level identifier with `oabCosmetic`, and making `oabIsWhitelisted` a single shared definition (declared once, in `cosmetic-filter.js`, which loads first) instead of two independent copies. This class of bug is easy to reintroduce - any new top-level `let`/`const`/`function` added to either content script must be checked against the other file's identifiers.

2. **Coverage-ratio blind spot for standard-size ad units.** Once the engine actually ran, it still missed the real site's ad: a `position: fixed`, `z-index: 100`, 728×90px banner overlapping the video player. Its viewport-coverage ratio was only ~7% (728×90 in a 1280×720 viewport), under the 15% floor required for the coverage signal to contribute anything - because IAB standard ad-unit sizes (728×90, 300×250, etc.) are deliberately small in absolute pixels, coverage-% alone systematically underweights exactly this common pattern. Fixed by adding a dedicated signal: fixed/sticky-positioned elements whose bounding box matches a standard IAB ad size (±4px tolerance) get +3 regardless of coverage %. Also added "banner"/"bnr" to the ad-keyword list, which was missing despite being one of the most common ad-related class/id substrings in the wild.

3. **False positive from the "paywall" keyword.** In tightening the above, `paywall` was included in the ad-keyword list from the first draft. Retesting the fixture page (which includes a negative-control paywall banner) after the fix above showed it now incorrectly scored 6 (exactly at threshold) and got hidden. Removed `paywall` from the keyword list - not just because it's a false-positive source, but because auto-hiding paywalls is a materially different feature (paywall bypass) from ad-blocking, and out of scope regardless of scoring accuracy.

After all three fixes: the fixture page's three negative controls (login modal, cookie banner, paywall) all stay visible, both positive fixtures behave as designed, and the real site's overlay banner is correctly hidden with no other visible regressions. **Takeaway for future changes to these two files**: fixture-page testing alone did not catch either the namespace collision (the fixture page happened not to exercise a rescan path that touched the broken function before the crash was found via a real site) or the coverage blind spot (no fixture used a small, standard-size, low-coverage ad) - real-site testing remains necessary before trusting a change to the heuristic engine.

### Finding 4 (same session, discovered by the user manually testing): clickunder popunder ads - a new attack class, new file added

Manually clicking the play button on the same real site opened a new tab to a rotating ad/gambling/scam destination (URL literally tagged `clickunder`, the ad-network's own name for the format). This is architecturally different from everything else in this project: there is no DOM element to hide - the redirect is triggered by a JS click-interception calling `window.open()`, so `overlay-engine.js` and `cosmetic-filter.js` are structurally incapable of addressing it no matter how they're tuned.

**Fix: added `content-scripts/popunder-guard.js`**, a new content script that overrides `window.open` to block cross-origin popups (allowlisting common OAuth/payment flows: Google/Apple/Microsoft login, PayPal/Stripe checkout, a few social platforms). Getting it to actually work took three iterations, each caught by testing against the real, live attack rather than reasoning about it in the abstract:

1. **First attempt only patched the top frame.** `window.open` in an isolated content-script world is a different function object than the page's own - overriding it there has zero effect on page JS. Fix: this script must run in the `"world": "MAIN"` (declared per-file in a separate `content_scripts` entry, since `world` applies per-entry, not per-file). MAIN-world scripts have no `chrome.storage`/`chrome.runtime` access at all (hard platform restriction), so respecting the enabled/whitelist state requires a bridge: `cosmetic-filter.js` (isolated world, has storage access) now also writes `data-oab-enabled` onto `document.documentElement`, which `popunder-guard.js` reads synchronously on every `window.open` call.
2. **Still fired from inside the embedded video-player iframe** (a cross-origin `<iframe>` with its own separate `window.open`) - `all_frames: false` (the same scope limitation already documented for the other two scripts) left it completely unpatched there. Fix: set `all_frames: true` specifically for this one script - justified here in a way it isn't for the heavier scripts, since a single function-override has negligible per-frame cost compared to continuous DOM scanning.
3. **Still fired from an `about:blank` frame even with `all_frames: true`.** Chrome/Firefox do not inject content scripts into `about:blank`/`about:srcdoc` frames at all by default, regardless of `all_frames`, because those frames have no real URL to test the `matches` pattern against - and that's exactly where a lot of ad-tag script executes (a dynamically created iframe with content written in via `document.write`). Fix: added `"match_origin_as_fallback": true`, which makes the browser use the initiating frame's origin as the match target for these URL-less frames.

Verified with 8 repeated live trials after all three fixes: 0/8 popups got through (vs. roughly half getting through in earlier trials before the fixes), with the guard's own "blocked a cross-origin popup" warning firing on every attempt - including cases where the ad script visibly retried against multiple rotating destination domains within a single click.

**Documented, accepted trade-off**: the `data-oab-enabled` bridge only exists in the top frame (the only frame `cosmetic-filter.js` runs in). Inside sub-frames, `popunder-guard.js` always falls back to its safe default (blocking active) regardless of the user's global toggle or per-site whitelist - i.e. whitelisting a site to stop cosmetic/overlay hiding does not also disarm popup blocking inside an embedded third-party iframe on that site. This is intentional, not an oversight, but is a real behavior difference worth knowing about.

**Takeaway**: this finding class (clickunder/popunder) would not have been caught by fixture-page testing or code review at all - it requires an actual malicious ad network in the loop, which only live-site testing provides. Anyone extending ad-blocking coverage further should expect to find similarly-invisible mechanisms (redirect chains, `location` reassignment, etc.) that also don't manifest as inspectable DOM state.

### Finding 5: tested against canyoublockit.com/extreme-test/ (a purpose-built ad-blocker test site) - two more real issues

This site is safe, legitimate, and designed exactly for this ("This page is full of the scummiest adverts out there... Do not trust anything on this page"), so it's a better default choice than a random ad-heavy site for future testing.

1. **Ad-blocker-circumvention network partially evades the curated domain list.** The site's ads are served via `adsco.re` / `antiadblocksystems.com` - services whose entire product is defeating ad blockers, by proxying ad creative through per-load randomized subdomains and even fully separate random-looking domains (`fvcwqkkqmuv.com`, `ybs2ffs7v.com`, etc.). Added the two stable, named domains to `domains-source.txt` (catches their subdomains via `||domain^`), but **retesting confirmed the actual banner images still load** - the loader domain got blocked, but ad creative is served through a different, freshly-randomized domain each time that no static list can enumerate in advance. This is not a bug to fix; it's the curated-list approach hitting its documented, inherent ceiling. Beating this class of network reliably would require a maintained, actively-updated filter list (EasyList-class scale/tooling) or path/pattern-based rules rather than domain listing - a real "graduate to a bigger list" decision, not an MVP fix.
2. **Keyword-matching bug via hex-hash false match (found, fixed).** A legitimate Mopinion customer-feedback survey widget got auto-hidden. Root cause, found via full (non-truncated) debug output: `oabMatchesAdKeyword` tokenizes on any non-letter character, so a random hex ID like `surveyWindowWrap-40ea9b0799ad6c6bd5d8fe24139f507c74b5b0ea` gets fragmented at digit boundaries, and the substring `9ad6` produces an isolated `"ad"` token - a pure coincidence with nothing to do with advertising, but it matched the keyword list anyway. **Fixed**: strip runs of 8+ hex characters from `id`/`className` before tokenizing (`OAB_HEX_RUN_RE`), so auto-generated hashes (extremely common in modern component frameworks) can't masquerade as keyword hits. This is a real, generally-applicable correctness fix, not specific to this one site.
   - **However, fixing the keyword bug alone does not stop this specific element from being hidden**: its score without the keyword point is still `position(3) + coverage(4) + delayed(1) = 8`, comfortably over threshold, because the survey widget briefly renders at near-full-viewport size on a delay - the same position+coverage+delay combination a real full-screen interstitial ad would have. This is the already-documented structural false-positive risk (paywalls, cookie banners, onboarding modals) with one more legitimate pattern added to the list: **delayed full-screen feedback/survey prompts**. Deliberately did not weaken the coverage/position/delay signals to accommodate this - doing so would blunt detection of the real full-screen ad interstitials those signals exist to catch. The per-site whitelist and "restore hidden elements" popup button remain the intended mitigation for this class of false positive, not further heuristic tuning per legitimate-widget-vendor.
